## 1. Domains — a real test, and what it found

The question was whether a merchant can genuinely attach a domain. So: added
one through the real screen, read the records it asked for, checked it against
live DNS, promoted it, made it the main address, served the storefront on it,
and removed it — then put the database back.

**Works, and was proved:** the add form's live validation, real DNS lookups
cross-checked against `dig`, the records shown, the primary switch (enforced by
a unique index, not just code), the storefront serving on the custom host, the
free address redirecting to it, an unknown host 404ing, and removal handing
"main" back to the free address.

**Three faults:**

**Nothing checked a domain unless a person pressed the button.** The code said
in three places that "the checker runs on a schedule". There was no schedule,
and `verifyDomain` had exactly one caller. A merchant who corrected their DNS
overnight stayed pending until they came back and pressed it; a domain that
broke after going live was never noticed at all — the screen went on saying
"live" while the store was gone. `backoffMs` and `MAX_AUTOMATIC_CHECKS` had
been written for a caller that did not exist.

Fixing it introduced a worse risk, handled in the same commit: **a live domain
now survives three consecutive failures before it stops being served.**
Demoting on the first would take a working store off its own domain because one
DNS query was unlucky. Refusing to serve a domain that works is a far worse
mistake than serving one whose records have just been removed.

**The apex address we handed out was the host's old one.** We printed one
address and accepted only that exact string; the host now issues another, and
both route. A merchant whose apex was already correct — `norishba.com` is
exactly that — was told their records were wrong with nothing they could do
about it. `DNS_TARGET.accepts` is a list now: print the first, take any, and
the printed one is always in the list.

**The canonical redirect was a 307 under a comment saying "permanently".** A
search engine reads 307 as "keep the old address indexed", which is the one
thing that redirect exists to prevent. Measured at 308 now.

**Still untested, and needs a domain whose DNS can be changed:** whether the
host accepts our CNAME target, issues the certificate, and flips a domain to
live.

## 2. Motion — and the accessibility fault underneath it

The ask was animation across the panel. The panel already had press feedback on
every button and a progress bar on link clicks; what had no motion at all were
the things that appeared and vanished. One of those turned out not to be
cosmetic.

**Nineteen screens across the admin, the customizer and the storefront had each
written their own rose error paragraph, and most carried no `role`.** A screen
reader announced nothing, so a merchant who could not see the message watched
the save do nothing, twice, forever. They all go through `FieldError` now:
`role="alert"`, and `.notice-in`, which opens its own height so the form below
slides rather than being shoved.

Dialogs and toasts arrive and leave. A toast is marked leaving, plays its exit,
and is removed when that finishes — the removal timer and the CSS duration are
asserted equal, because a shorter timer blinks it out and a longer one holds
its neighbours down.

**A navigation the app started itself showed nothing.** The progress bar
listened for anchor clicks only, so signing in, saving a product and switching
page in the customizer all left the screen looking dead. `startNavProgress()`
covers those. The list filter is deliberately excluded — it replaces the URL on
every keystroke.

**My own bug, worth keeping:** the leaving-toast set was first read inside the
state updater. React invokes updaters twice in development, so the second
invocation saw the first one's result, concluded the toast was already leaving,
and never scheduled the removal — the toast sat there faded forever. It is a
ref now.

## 3. Maintenance — one page, and the merchant's words

Asked for: a maintenance section under Your App with a way to change what the
page says, and the toggle out of Preferences.

**The real fault was not where the toggle lived.** Pausing a store and turning
maintenance mode on showed customers two completely different notices, both
hard-coded where no merchant could reach them, and neither screen mentioned the
other existed. Pause for the afternoon and you had no idea what your customers
were being shown.

One page for both now, and the words are the merchant's. Empty means "use
ours", stored empty rather than seeded — seeding would freeze today's copy in
every row, so improving it later would reach nobody. Fallback is per field.

**Closed, suspended and blocked keep our wording and are not editable.** A
store that has shut for good must not tell someone waiting on an order to check
back later; a suspension is not the merchant's to explain away; a blocked
visitor is not waiting for anything, because the store is open and simply will
not serve them.

**"Tell me when you reopen"** has its own table, not `Customer`. A `Customer`
has a required name, an address book and an order history; someone who typed
one field into a holding page has none of that, and writing them in would mean
inventing a name and dropping strangers into every count and export.

**Two truths found by testing rather than reading.** A paused shop is now told
so on this screen whatever the switch reads. And switching maintenance off
while paused no longer claims the store is visible — that sentence would be a
lie a merchant acts on.

**The toggle did not stay behind in Preferences.** `maintenanceMode` was
removed from the `Visibility` type, its form and its save action, because a
copy left there would have been worse than a duplicate control: that form
writes every field it holds, so hiding the store and later saving a blocked
country would have silently switched it back on.

## 4. The cron limit

The first deploy of the domain checker was **refused outright**: the hosting
plan allows one cron run per day and `43 * * * *` is more than one.

Hourly is what it wants — the backoff starts at a minute and doubles, so an
hourly schedule lets the backoff decide how often a registrar is asked, and a
daily one means the schedule decides and the backoff is decoration. What daily
costs: a merchant who fixes DNS at midnight goes live the next morning rather
than within the hour, unless they press Check now — which is now offered on
live domains too, so the slow path only affects merchants who have walked away,
who are exactly who a scheduled checker is for.

One line in `vercel.json` changes it back. Queued.

## 5. The guided type switch

`typeSwitchGate` already refused an open store and was already enforced at the
write. This was about the twenty seconds after the rule is stated.

The refusal carries two ways out — "Pause my store" for someone who knows what
that means, "Show me where" for someone who does not and who should come away
knowing where the control lives. `?show=pause` carries the hint across the
navigation; the receiving screen scrolls the control into view, plays
`.attention` for five seconds, and removes the parameter. Pausing then offers
the page it has just put in front of every customer, with three answers rather
than two.

Closed and suspended get the refusal *without* the link, because pausing fixes
neither and pointing at the button would send someone to press a control that
changes nothing.

**Three of my own faults, all found by driving it rather than reading it.** The
class was left on the control for the life of the screen. Fixing that naively
then stripped it a frame after it went on, because clearing the parameter
re-ran the effect and its cleanup. And `.attention` was matched by a comment on
the analytics screen about "a number competing for attention". The hook reads
the parameter once on arrival and never again — which is also the honest
description of what a hint is.

## 6. The shop's marks

Asked for: a favicon in formats that work, logos for dark and light and for
phone and desktop, themes that read this screen, and logos changeable nowhere
else.

**The reason they had to move is not the reason that was asked for.** Logos
were theme tokens, and theme tokens are stored per business type — so a
merchant who switched from a shop to a restaurant lost their logo, and lost it
again switching back. The same company, the same artwork, two storefronts each
holding half of it. A logo is identity, not style.

Four slots on two axes plus the favicon, on `StoreSettings`. `pickLogo` walks a
chosen fallback order so a theme may ask for any combination and is never
handed nothing. Where it is ambiguous, **shape beats colour**: a wordmark that
does not fit is illegible, one in the wrong tone is merely wrong.

**The migration's first draft lost artwork.** It preferred the live business
type before it preferred a row that actually *had* a logo, which silently lost
the work of every merchant who uploaded it under a type they later switched
away from. Logo and favicon are picked independently now, presence before type.
Five cases tested against the database — and the fault only showed because case
two existed in the test at all.

**Two more faults found on the way.** A shop with no logo rendered
`/logo.svg` — *this platform's own mark* — in its header, on every storefront
that had never uploaded one, while Home had always said the store name would be
used. And the settings search still sent anyone typing "upload logo" to the
theme panel, the one screen that no longer has it.

**The favicon is restricted to SVG, PNG and ICO.** WebP is the trap: it
previews perfectly in the panel and draws a blank square on a browser tab.

Proof it worked: after deploying, `ahad1v.shop.synoradigitals.com` renders its
logo **from the new column** — the backfill carried it out of the theme tokens.

## 7. The alignment audit

All twenty-nine screens measured in a browser and cross-checked against source.

**Already right, and measured rather than assumed:** every screen's sections
start and end at exactly the same pixel (262 / 1458 in a 1512px window), and no
screen has ragged card bottoms.

**Fixed.** Four styles were naming the same thing — 14px medium, 14px
semibold, 12px semibold uppercase, 12px medium uppercase — and on Your App →
Themes, two of them sat a few hundred pixels apart. Five more headings were
written as `<p>`, so nothing in the page outline knew they named anything. The
rule was already written down; only `Fieldset` followed it, because **a rule
with no primitive behind it is a convention, and a convention is what produced
the four.** `CardTitle` and `GroupLabel` exist now and twenty headings go
through them.

The gap between sections was six values across thirty-three screens. Only
Analytics showed it; the rest was latent. Site text rows stopped 290px short of
the rule beneath them.

**Two flagged screens were investigated and cleared rather than changed.**
Custom fields is a deliberate master–detail layout; Menus' odd inset is a row
container inside a card that my probe's nesting filter missed.

**Two of my own measurements were artefacts and were thrown away** — an
apparent 16px width difference on Analytics was a probe stopping at different
depths per screen, and a section-finder anchored on `.bg-panel`, which also
matches sidebar buttons, so it found nothing on 25 of 26 screens.

## What changed about how this gets shipped

**A push to GitHub does not deploy this project.** Verified: no build fires,
`synora-shop-git-main` stays put, and there are no GitHub Actions. Every
production deploy has been made by hand with `vercel --prod`. The standing note
saying otherwise has been corrected.

**Deploying is what runs migrations** — `npm run build` begins with
`migrate-deploy.mjs`. So the thing to ask about is the deploy, not the push.

To deploy without shipping unfinished local work: clone to a scratch directory,
check out the approved commit, copy `.vercel/` across, deploy from there. Used
twice today, once because the working tree held an unapproved migration.
